# 快办（KuaiBan）— 技术选型 v0.1

> 配套文档：[快办-业务逻辑设计-v0.2.md](./快办-业务逻辑设计-v0.2.md)
> 目标：选一套**能覆盖 Windows / macOS / Android / 鸿蒙 / iOS 五个平台**且业务代码只写一遍的技术栈。

---

## 0. 选型结论（先看这里）

| 层 | 选型 |
|---|---|
| **开发语言** | **TypeScript**（客户端、服务端、管理后台全用同一门语言） |
| **界面** | **Web 技术**（Vue 3 + Vite + TypeScript） |
| **大脑** | **纯 TypeScript 包**，零平台依赖，全平台 100% 复用 |
| **客户端外壳** | **Tauri 2**（Windows / macOS / Android / iOS 官方支持；鸿蒙走社区已验证方案） |
| **本地存储** | SQLite |
| **服务端** | Node.js + Fastify + PostgreSQL，Docker 部署 |
| **认证** | JWT 长效令牌（配合离线优先） |
| **代码组织** | pnpm monorepo（一个仓库，多个包） |

**一句话**：**Web 写界面 + TypeScript 写大脑 + Tauri 做外壳 + Node 做服务端。**

---

## 1. 为什么是这套（对比过程）

### 1.1 候选方案

| 方案 | Windows 挂件 | Android/iOS | 鸿蒙 | 体积 | 界面复用 |
|---|---|---|---|---|---|
| **Electron** | ✅ 最成熟 | ❌ 不支持 | ❌ 不支持 | ❌ 100MB+ | Web |
| **Tauri 2** | ✅ 支持 | ✅ 官方支持 | ⚠️ 社区 fork，已验证可行 | ✅ **5–15MB** | Web |
| **Flutter** | ⚠️ 需插件 | ✅ 支持 | ⚠️ 社区分支 | ✅ 30–50MB | Dart |
| **uni-app x** | ❌ 无桌面端 | ✅ 支持 | ✅ **官方支持**（编译为 ArkTS） | ✅ 小 | Vue 语法 |
| **原生分平台** | ✅ | ✅ | ✅ | ✅ | ❌ 各写一遍 |

### 1.2 关键情报（已核实）

**① Tauri 的鸿蒙路径是真实可行的。**
社区维护的 Tauri OHOS 分支（[richerfu/tauri · feat/open-harmony](https://github.com/richerfu/tauri/tree/feat/open-harmony)）已能完成鸿蒙 PC 的完整移植，原理是：Rust 后端交叉编译成 `.so` → 前端零改动塞进 rawfile → DevEco 工程壳 → 打包 HAP。有 2026 年 8 月的[完整实战记录](https://www.cnblogs.com/qq8864/articles/22508425)（含 12 条避坑清单），说明这条路已被走通。
官方仓库另有 [HarmonyOS 适配 issue #11112](https://github.com/tauri-apps/tauri/issues/11112) 跟踪，但**尚无官方支持**——鸿蒙仍是社区方案。

**② uni-app x 从 4.61+ 起官方支持纯血鸿蒙 NEXT**，把代码编译成运行在 ArkTS 引擎上的鸿蒙原生应用，同时支持 Android / iOS。HBuilderX 4.71+ 还支持了鸿蒙 PC 开发。详见[官方文档](https://doc.dcloud.net.cn/uni-app-x/app-harmony/)。
但官方文档自己也写明："**鸿蒙整体处于发展初期，能用，有坑**……建议降低期望，不能严格比照 Android 和 iOS 的验收标准。"
**致命短板：uni-app x 没有桌面端**——做不了"贴边挂件、不抢焦点"这种重型系统集成。

**③ Electron 没有鸿蒙、也没有移动端。**

### 1.3 为什么最终选 Tauri

按你自己的三条要求逐条打分：

| 你的要求 | Tauri | 说明 |
|---|---|---|
| **软件不要过于庞大** | ✅ | 安装包 5–15MB，Electron 是它的 10 倍 |
| **速度要快** | ✅ | 用系统自带 WebView，启动和内存都远优于 Electron |
| **功能不要复杂** | ✅ | 复杂度被"大脑/外壳分离"隔离掉了 |
| **多端技术栈互通** | ✅ | **同一套 Web 界面 + 同一个 TypeScript 大脑，覆盖 5 个平台** |

**别的方案做不到"一套界面覆盖 5 个平台"**：
- Flutter 能覆盖 5 个平台，但要学 Dart，且桌面挂件要依赖第三方插件硬撑
- uni-app x 鸿蒙最好，但**做不了桌面挂件**
- Electron 桌面最舒服，但**上不了手机**

Tauri 是唯一一个**桌面能力够用 + 能上移动端 + 鸿蒙有活路 + 体积小**的选择。

## 2. 架构：四层分离（最重要的一节）

```
┌──────────────────────────────────────────────────────────┐
│  ① 界面层    Vue 3 + Web 技术                              │
│     5 个平台共用同一套界面代码（响应式适配桌面/手机）          │
├──────────────────────────────────────────────────────────┤
│  ② 大脑层    纯 TypeScript，零平台依赖                      │
│     待办规则 / 重复规则 / 逾期顺延 / 提醒调度                 │
│     ★ 100% 全平台复用，一行都不用改 ★                       │
├──────────────────────────────────────────────────────────┤
│  ③ 平台桥接层  统一接口，各平台各写实现                       │
│     存储 / 通知 / 声音 / 窗口 / 托盘 / 自启 / 网络            │
├──────────────────────────────────────────────────────────┤
│  ④ 外壳层    Tauri（Windows / macOS / Android / iOS / 鸿蒙）│
└──────────────────────────────────────────────────────────┘
                    ↕ HTTPS
┌──────────────────────────────────────────────────────────┐
│  服务端    Node.js + TypeScript（与大脑同语言，共享类型定义）  │
│            Fastify + PostgreSQL + Docker                   │
└──────────────────────────────────────────────────────────┘
```

### 2.1 一条必须写进规范的铁律

> **`packages/core`（大脑）里绝对不允许出现任何平台专属代码。**
> 不许 import 窗口、托盘、通知、文件系统、HTTP 客户端。
> 所有平台能力必须通过**接口**注入。

**为什么这条是铁律**：未来加一个平台时，如果你发现大脑里散落着 `if (isWindows)`，那"技术栈互通"就失败了，每个平台都要改大脑——那就退化成"各写一遍"了。

**检验方法**（很朴素但有效）：大脑包的代码能在纯 Node 环境下跑单元测试，不报任何平台错误。做到这一点，就证明它真的零依赖。

### 2.2 界面的响应式策略

同一套界面，桌面和手机形态差别很大：

| 平台 | 界面形态 |
|---|---|
| Windows / macOS | 贴边挂件，宽 320–360px 竖长面板 |
| Android / iOS / 鸿蒙 | 全屏 App，底部 Tab 切换四个模块 |

**做法**：界面组件共用，布局用断点切换。桌面端额外实现"挂件外壳"（贴边、悬停、不抢焦点），移动端用标准 App 框架。**业务组件一行不改。**

## 3. 各平台实现路径

| 顺序 | 平台 | 实现方式 | 难度 | 备注 |
|---|---|---|---|---|
| 1 | **Windows** | Tauri 2 桌面 | 中 | 第一版重点 |
| 2 | macOS | Tauri 2 桌面 | 低 | 换外壳，大脑/界面不动 |
| 3 | Android | Tauri 2 mobile | 中 | 界面改响应式布局 |
| 4 | 鸿蒙 | Tauri OHOS 社区分支 | **高** | 届时再决策，见第 7 节 |
| 5 | iOS | Tauri 2 mobile | 中 | 需 Mac + 开发者账号 |

### 3.1 Windows 挂件要用的系统能力

| 需求 | 方案 |
|---|---|
| 无边框贴边窗口 | Tauri `decorations: false` + `transparent` + `always_on_top` |
| 不占任务栏 | `skip_taskbar: true` |
| **不抢焦点** | Rust 侧设置 `WS_EX_NOACTIVATE`（需少量平台代码，隔离在桥接层） |
| 鼠标穿透 | Tauri `set_ignore_cursor_events` |
| 托盘图标 | `tauri-plugin-tray` |
| 开机自启 | `tauri-plugin-autostart` |
| 系统通知 | `tauri-plugin-notification` |
| 声音 | 前端播放音频 / 系统提示音 |
| 全局快捷键 | `tauri-plugin-global-shortcut` |
| 本地数据库 | `tauri-plugin-sql`（SQLite） |
| 自动更新 | `tauri-plugin-updater` |

> ⚠️ **唯一需要写 Rust 的地方就是"不抢焦点"这个窗口行为**，而且它被关在桥接层里，不会污染大脑和界面。

## 4. 技术栈清单

### 4.1 客户端

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 全栈统一 |
| 框架 | Vue 3 + Vite | 中文资料多、上手快、构建快 |
| 状态管理 | Pinia | Vue 3 标准搭配 |
| UI | **轻量自研样式**（不引大型组件库） | 界面简单且要定制，大组件库拖慢启动、增大体积 |
| 时间处理 | Day.js | 比 Moment 小得多 |
| 桌面外壳 | Tauri 2 | 见上 |
| 本地数据库 | SQLite（`tauri-plugin-sql`） | 单文件、快、可整体拷贝 |

### 4.2 服务端

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js 20+ | 与客户端同语言 |
| 框架 | Fastify | 轻、快、插件生态好 |
| 数据库 | PostgreSQL | 50 人以内绰绰有余；备份工具成熟 |
| ORM | Drizzle | 类型安全、轻量、SQL 直观 |
| 认证 | JWT（长效 refresh token） | 支持离线优先 |
| 部署 | Docker Compose | 一键起 `api + postgres + HTTPS 网关` |
| HTTPS | Caddy | 自动申请和续期证书，**不担心证书过期** |

> 用 Caddy 是刻意的：业务逻辑文档里提到"证书过期 = 全员连不上"，Caddy 自动续期直接消灭这个风险。

### 4.3 管理后台

- 复用同一套 Vue 3 + TypeScript 技术栈
- 一个简单的网页，构建后由服务端托管
- **接口层面就不提供"查看用户待办内容"的能力**

### 4.4 代码组织（monorepo）

```
KUAIBAN/
├── packages/
│   ├── core/          ★ 大脑：纯 TS，零平台依赖，全平台复用
│   ├── shared/            类型定义、常量（客户端 + 服务端共用）
│   └── ui/                界面组件（桌面 + 移动共用）
├── apps/
│   ├── desktop/           Tauri 外壳 → Windows / macOS / Android / iOS
│   ├── server/            Node 服务端
│   └── admin/             管理后台网页
├── docs/                  设计文档
└── package.json           pnpm workspace
```

**未来加平台的成本**：新增 `apps/mobile-harmony` 一个目录，`packages/core` 和 `packages/ui` 不动。

## 5. 本地开发环境（现在就能跑起来）

你要求"先在本地开发环境开始，完成后再部署到服务器"，正好符合这套栈：

| 组件 | 本地怎么跑 |
|---|---|
| 客户端 | `pnpm tauri dev` → 直接在本机弹出窗口调试 |
| 服务端 | `docker compose up` → 本机起 Node + PostgreSQL |
| 管理后台 | `pnpm dev` → 浏览器打开 |
| 数据库 | Docker 里的 PostgreSQL，随时可清空重建 |

**开发和部署用的是同一份 Docker 配置**，本地跑通 = 服务器上也能跑通，"在我机器上好好的"问题基本消失。

## 6. 一个必须提前解决的现实问题

**你的开发机是 Mac（M1），但第一版目标是 Windows。**

Tauri 不容易从 Mac 直接交叉编译出 Windows 安装包，而且——

> ⚠️ **"贴边挂件、不抢焦点、托盘、开机自启"这些行为，在 Mac 上根本验证不了。**
> 它们全是 Windows 特有的系统行为。

三条路线可选：

| 路线 | 说明 | 适合 |
|---|---|---|
| **A. Mac 开发 + 服务器/CI 出 Windows 包** | 代码在 Mac 写，用一台 Windows 构建机（或 CI）打包并做人工验证 | 开发体验最顺 |
| **B. Mac 开发 + Windows 虚拟机验证** | M1 上跑 Parallels / UTM 装 Windows 11 ARM | 随时能验证，但虚拟机里某些系统行为仍可能与真机有差异 |
| **C. 直接用 Windows 开发机** | 全流程都在 Windows 上 | 最靠谱，但需换机器 |

**我建议 A + B 结合**：日常在 Mac 上开发；挂件相关改动用 Windows 虚拟机快速验证；每个版本用一台真 Windows 机器做一次最终验收。

## 7. 鸿蒙专项说明（诚实版）

鸿蒙排在第 4 位，是整个路线图里**唯一没有官方跨平台支持**的平台。到那时有两条路：

### 路线一：Tauri OHOS 社区分支（推荐先试）
- **优点**：界面和大脑**零改动**，只换外壳，符合"技术栈互通"
- **缺点**：社区分支，非官方；构建流程繁琐（需要 DevEco Studio、交叉编译、手工装配 HAP）；有十几个已知坑
- **风险**：分支可能跟不上 Tauri 官方版本

### 路线二：鸿蒙外壳用 ArkTS 重写
- **优点**：官方支持，质量最可控
- **缺点**：**界面要重写一遍**（大脑仍可复用，但鸿蒙用 ArkTS，不能直接跑 TypeScript 大脑，需要把大脑逻辑做成可跨语言调用的形态）

### 现在的决策

> **不要为了鸿蒙牺牲 Windows 第一版的质量和进度。**
> 鸿蒙是最后一个目标，届时（很可能是一年后）生态会大不一样。
> 现在要做的只有一件事：**守住"大脑零平台依赖"这条铁律**。
> 只要守住它，将来无论走哪条路，最坏情况也只是"重写外壳"，而不是"重写整个软件"。

## 8. 风险与回退方案

| 风险 | 概率 | 回退方案 |
|---|---|---|
| Tauri 的"不抢焦点挂件"实现困难 | 中 | **换 Electron 外壳**——因为界面是 Web、大脑是纯 TS，**只换外壳，不改业务代码** |
| Tauri 生态某个插件缺失 | 中 | 写一小段 Rust，隔离在桥接层 |
| 鸿蒙路线届时走不通 | 中 | 用 ArkTS 重写外壳，复用大脑 |
| 移动端手感不如原生 | 中 | 移动端后期可考虑独立实现 UI，大脑仍复用 |
| Mac 上开发 Windows 版效率低 | 高 | 见第 6 节的 A+B 方案 |

**注意"回退方案"这一列全都是"换外壳"** —— 这正是四层分离架构的价值：**技术选型可以试错，业务代码不会白写。**

## 9. 这套选型如何满足你的原始要求

| 你的原话 | 如何满足 |
|---|---|
| "软件一定不要过于庞大" | Tauri 安装包 5–15MB；不引大型 UI 组件库 |
| "功能不要过于复杂" | 四层分离，复杂度被隔离；功能边界已明确砍到 8 项 |
| "速度要快" | 系统 WebView + SQLite + 本地优先，打开到可输入 < 200ms |
| "使用简单" | 登录一次永久记住；全局快捷键极速记录；悬停即用 |
| "多端技术栈必须互通" | 一套 TypeScript 大脑 + 一套 Web 界面，覆盖 5 个平台 |
| "本地先开发，最后部署服务器" | Docker 配置本地与线上完全一致 |
