## 【WAL 备份修法】

**✅ 已实施**（你们说"不需要等你们、按我们节奏执行"，已完成）。

**问题实测确认（为什么必须修）**：

| 文件 | 大小 |
|---|---|
| `kuaiban.db`（主库） | 49 KB |
| `kuaiban.db-wal` | **387 KB** |

⇒ **数据几乎全在 WAL 里**；原"整目录 tar"在写入瞬间若拿到错配组合，备份基本等于空。

**修法**：每日备份打包**之前**，让**运行中的容器**用它自带的 `node:sqlite` 执行 `VACUUM INTO` 生成**原子快照**，用快照**替换**待打包的主库并删掉 `-wal`/`-shm`。
- **无需安装任何软件**、**不中断服务**
- **恢复方式完全不变**（仍是解包还原到 `/opt/kuaiban/data`）
- 容器未运行或快照失败 ⇒ 退回原样打包并**记录具体原因**，不阻断备份

**验证（三层）**：
1. 完整备份端到端（落点在临时目录，真实备份目录未受影响、未触发轮转删除）→ ✅ 成功
2. 备份包内只剩 `kuaiban.db` + `releases/`，**已无 `-wal`/`-shm`** → ✅
3. **把备份包里的库解出来与线上库逐表比对**：
   - 测试机：`表数=4 ｜ sync_records=20  tokens=8  users=2 ｜ integrity=ok` — **与线上完全一致**
   - 生产机：`表数=4 ｜ settings=1  tokens=3  users=1 ｜ integrity=ok` — **与线上完全一致**

**回滚点**（万一需要）：两台均保留 `/usr/local/sbin/server-backup.sh.bak-pre-sqlite-20261004`。

**附带提醒（供你们评估）**：加入客户端安装包缓存后，每日备份包从约 0.7 MB 涨到约 **20 MB**。当前保留策略（日 7 / 周 4 / 月 6）下约 **300 MB 量级**，可接受。若后续发版频繁导致体积明显增长，我们会考虑排除 `releases/`（它们可从 GitHub Release 重新获取，非不可再生数据）——**这属于我们内部优化，不需要你们做任何事**。
